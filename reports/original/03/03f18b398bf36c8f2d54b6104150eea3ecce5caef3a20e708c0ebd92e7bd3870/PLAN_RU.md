# TS-LM-PREFETCH-DIFF-v1 — один prospective frozen запуск

Статус: **PREPARED_NOT_STARTED / требуется согласование нового исполнения**. TS-LM-DISK-v1 остаётся PASS только хранения и finite byte-contract. Его файлы, P01 и научные результаты не изменены. Ни одной новой Perl-команды, compile-only, broker/glue или IPC-попытки при подготовке не было.

## Цель и неизменная вычислительная часть

Проверить минимальный новый слой: disk lookup → bounded IPC → raw Perl strings → шесть малых обычных hash → **byte-identical JMSmoothing.pm** из commit `2c7ad49cd4f4fa852168a8ce295bf739bf076adc`. ReadLM/Utils/NoSpace тоже неизменны. Тела MCTS/Selection/Expansion/Backpropagation/GetSuccessors/Insert/Assume совпадают с прежним traced fixture harness; наблюдатели перечислены в `evidence/COMPUTE_OBSERVERS.diff`. Полный оригинальный `masc_solver_mcts.pl` — только доказательный исходник, его entrypoint запрещён.

Oracle читает только малые fixtures оригинальным ReadLM и вызывает сохранённую ссылку на оригинальный ProbCharWord. Adapted получает те же leaf-строки через Prefetch; Python не применяет truth, floating point, backoff или score. Prefetch использует оригинальный `replace_unknowns`; материализует U, затем нужные bi/trigrams N. Повторный вызов `replace_unknowns` внутри JMSmoothing сохраняется. Отсутствующие листья не вставляются, autovivification происходит штатно в локальных Perl-hash.

Ключи/значения — ASCII bytes, число остаётся строкой через hex/pack. Generic ReadLM-input с пустым значением/неправильными полями/Unicode не поддерживается: это вне доказанного домена pinned LM и должно отвергаться, а не нормализоваться. Пустая входная строка scorer проверяется отдельно. Никакого изменения NoSpace, словаря, maxlen, списков/дублей patlst, lambdas, strict `>` или порядка операций.

## Единственная последовательность

1. T0 в `launch.py`; отказ при существующем launch marker или attempt. Полные hashes малого пакета/runtime, ресурсный gate и точная проверка prior PID/NSpid/starttime/argv. Никакого retry/resume.
2. **Reference**, затем **adapted + Python broker**, последовательно. Три сохранённых synthetic ciphertext длины6 (`abcabc` с корнями `cat`/`dog`, `ababab` с `to`), по2 MCTS-итерации. Это проверка интеграции прежних fixtures, не новая калибровка или атака. `n=1`, ngramorder3, patternlimit50, UCB C=1, x=0.05; исходные lambdas в harness. RNG-вызовов нет; `PERL_HASH_SEED=2026101705`, `PERL_PERTURB_KEYS=0`, `LC_ALL=C`, `TZ=UTC` одинаковы. В base LM строки стабильным образом отсортированы только при создании малых fixtures; значения и last-write сохранены. Реальные таблицы не преобразуются.
3. В тех же двух Perl-вызовах edge-fixtures: raw `0`/`00`/`0.00`, точные длинные десятичные строки и exponent, duplicate-last-write, missing, оригинальный unknown replacement; 11 combined-score проб, включая ровно две ожидаемые ошибки `log(0)`; отсутствие higher orders; две заведомо равные оценки `abc`/`bcd` и строгий Insert в двух порядках. Все ожидаемые структуры/индексы отказов фиксированы в fixtures. Adapted дополнительно отвергает11 malformed response fixtures через тот же parser, что читает реальные ответы.
4. Сразу сравнить **все320 trace events побайтно**, включая score bits (`pack d<`), segmentation, ordered candidates, keys, ties, шесть позиций inverse каждого принятого конструктивного состояния. Первые300 событий должны также совпасть с сохранённой старой reference; её64 score calls не переопределяются. Допуск численных расхождений **ноль**. Ровно158 broker requests, включая close. Любая новая ошибка/warning, иной отказ, неполная трасса или несовпадение — STOP, следующего подпункта нет.
5. **Только при PASS fixture и свежих memory gates**: проверить hashes исходных шести LM и шести уже verified offset-индексов; открыть их read-only. Один новый broker + один `transport_probe.pl`: 36 сохранённых byte lookup intents, затем8 фиксированных batches по776 (циклический повтор тех же36 в исходном порядке). Всего6244 запросов значений,35 различных ключей,10 IPC requests с close,58 response frames. Все raw values/last-row/missing сравниваются с уже сохранённым независимым reference. Ни одного score, текста-кандидата, MCTS или `.patlst` здесь нет. Измеряются время каждого roundtrip и всего участка: **≤10 с**, иначе STOP. Это первый пустой application-cache и повторные hot batches, не cold filesystem benchmark и не модель throughput поисковых кандидатов.
6. Сохранённые файлы/хеши, exit0, пустые доказанные process groups, неизменные входы и отсутствие OOM events — обязательны. Полный readback данных, без повторной математики. После исхода никаких автоматических действий.

## Пределы одного согласования

Один общий wallclock **180 с** от T0: проверки/загрузка runtime, reference/adapted, условный IPC, readback и cleanup. Первой части отведено90 с вместе с начальной подготовкой; условной второй — не более60 с и не позже общего срока. В каждой фазе4 с резервируются на TERM/2 с, KILL/2 с. Это внешний наблюдающий supervisor с кооперативным опросом50ms, не гарантированный realtime timeout.

Максимум одновременно **3 процесса**: supervisor и до двух детей. `launch.py` делает exec, не остаётся четвёртым процессом. Всего не более5 child invocations: reference Perl, adapted broker/Perl, условные real broker/Perl. Каждый процесс: **AS64 MiB**, CORE0, NOFILE64, отдельный файл≤8 MiB; CPU supervisor170/175 с, child45/50 с. Сумма AS-caps одновременно192 MiB. Logs/output≤32 MiB; IO/kernel/output allowance64 MiB. Это новый ограниченный инженерный scope, не понижение/подмена старого научного gate. Если64 MiB недостаточно — STOP без повышения.

Shared cgroup8 GiB, общий наблюдаемый abort при current≥7 GiB; новые OOM events означают STOP, остальные counters сохраняются. До малого исполнения: current + page-rounded small inputs +192 MiB +64 MiB <7 GiB. До полного hash чтения: current + page-rounded **все** pinned runtime/package/LM/index inputs +192 MiB +64 MiB <7 GiB. Ничего из cache не вычитается. После hashes: current +192 MiB +64 MiB <7 GiB. Race, dirty/writeback, внешние процессы и kernel reclaim не превращаются в гарантированный headroom; dedicated cgroup и новые security settings не создаются. Более низкие caps и малая структура не доказывают будущий search peak.

Недостаточный второй gate → `PASS_FIXTURE_REAL_SKIPPED_RESOURCE`, без ожидания очистки памяти и повтора. Это **не полный PASS**. Любая ошибка после начала допустимой части → STOP/UNKNOWN. Child gate до разрешающего байта ставит RLIMIT, публикует /proc; supervisor проверяет локальные/видимые PID, PGID, SID, NSpid, starttime и лимиты. Сигналы адресуются только собственной проверенной группе. Существующий process guard сохранён; текущий carrier допускается лишь при точном executable/командной строке и временном окне текущего запуска. Неизвестная идентичность — остановка, не сигнал наугад. Нет гарантии cleanup при потере host; такой исход UNKNOWN, без автоповтора.

## IPC и память

Две последовательные request/response фазы на score, без очереди встречных запросов. Request≤776 records, frame≤65536 B; replies≤128 records/chunk,≤7 chunks, с точными request id/offset/count/final. Источник value≤96 B, key token≤128 B; response raw strings никогда не JSON numbers. Новая компактная форма максимального128-record ответа —27021 B в собственном fixture. EOF, неправильная последовательность/форма/длина, numeric value, пропущенный final — STOP.

Broker не mmap и не грузит таблицы целиком. Readonly file handles, каждый pread≤512+16 B. Cache≤4096 entries для реальной пробы и3 для fixture; raw key/value payload≤1 966 080 B, Python object overhead дополнительно ограничен AS. Materialized Perl LM≤776 необходимых листьев на заявленном87-letter/одно-пробельном домене; здесь проверяются только короткие синтетические строки. Полные данные/offset indexes используются по SHA256, не имени; relocation требует явного нового path mapping до выполнения. Никакого rebuild `.patlst` или LM.

## Критерий решения

`PASS_FINITE_PREFETCH_AND_IPC_ONLY` требует всех сравнений, двух положительных частей, полного accounting/terminal evidence и сроков. Он разрешает **решить вопрос о подготовке следующего87-control**, но не запускать его. Пока не известны интеграция с production patlst broker, реальная генерация больших candidate lists, search peak/throughput и чувствительность. Если реальный IPC пропущен, точный вывод: numerical fixture (если он прошёл) проверен, транспорт на полных таблицах ещё не измерен. Ни сохранение bytes, ни finite bit equality не являются универсальным доказательством численной/траекторной эквивалентности или чувствительности.

## Граница нового исполнения

Согласование требуется ровно на `launch.py` → `run.py`/`child_gate.py` → `differential.pl` (reference/adapted), новый `Prefetch.pm`/`broker.py`, условный `transport_probe.pl`. Неизменённые авторские ReadLM/JMSmoothing/Utils/NoSpace выполняются только внутри этих fixtures. Библиотеки — уже установленные stdlib Python и core Perl JSON::PP/IO::Handle/Config/Time::HiRes; DBI/SQLite-модули Perl не нужны. Сети, installs, shell/date из author solver, личных файлов, новых настроек, full model hash-load, production solver, P01,87-control и Dorabella нет.

Риски: ошибка нового glue/синтаксиса, блокировка pipe до supervisor deadline, memory/CPU-cap, файловая гонка, transient shared-cgroup pressure и неполное завершение при сбое host. До/после hashes обнаруживают обычную смену входов, не доказывают невозможность кратковременной конкурентной подмены. Source paths и окружение должны оставаться подконтрольными сессии. Повышения прав и лимитов нет.

Полная команда, hashes всех запускаемых файлов, runtime identity и observed resource preview — в `FREEZE.json`/`RESOURCE_PREVIEW.json`. Сохранённые preparation byte/AST checks не запускают этот этап.
